# Pixel Play 审美复刻：像素树林、交互规格与风铃扩展

收录日期：2026-11-22

最近核实：2026-11-22，Asia/Shanghai

研究状态：部分核实。视频说明、抽样画面、FeralUI 首页、公开前端实现与素材下载入口已核对；未取得原始工程、作者完整提示词或风铃版源码，未做复刻验收。

## 一句话结论

这条不是在介绍一个新模型或“一键克隆工具”，而是 **把喜欢的视觉效果拆成外观、动作、控制项和验收标准，再交给编码 Agent 反复调整**。原项目是 FeralUI 的 Pixel Play；作者先复刻像素树林，再扩展为风铃。值得学的是如何把审美变成可执行规格，而不是把“几乎 1:1”当成已验证的能力承诺。 [S1–S4]

### 2. 原作不是简单的“程序画树＋纯物理”

原站发布包中的 “How it's made” 说明明确写道：

- **Drawn in Aseprite**：每棵树、叶子和花朵逐像素手绘。
- **Animated by hand**：Calm、Breezy、Storm 是手工关键帧动画，不是模拟。
- **Code only for touch**：摇树和掉叶会实时响应用户。 [S3]

这些是原站制作者的制作说明；没有独立审阅其 Aseprite 原文件。代码同时包含风场、拖拽和飞叶逻辑，不能把说明进一步推成“完全没有运行时计算”。比较准确的拆分是：**手绘/动画数据提供视觉基础，网页代码叠加交互、掉叶和显示控制。**

### 3. 已读到的原站运行结构

| 环节 | 公开发布代码中的证据 | 证据边界 |
| --- | --- | --- |
| 植物输入 | 初始化函数 `AP` 从 `/plants/<名称>.json` 加载植物数据 | 未取得或核验原始美术制作文件 |
| 像素显示 | CPU 路径使用 Canvas 2D、像素缓冲、`putImageData`，关闭 `imageSmoothingEnabled`；另有 WebGL 点/纹理渲染路径 | 不能笼统写成只用 Canvas、PixiJS 或 Three.js |
| 渲染选择 | `JB(...) || Xv(...)`；检测 WebGL context lost 后切换 CPU 路径 | 降级路径已读到，未做设备故障实测 |
| 风场 | `iP` 保存方向/强度/阵风，平滑更新，并用多个正弦分量构造随时间、位置变化的扰动 | 是视觉交互风场，不是工程级空气动力学 |
| 点击与拖拽 | 指针映射到场景像素，命中植物后 `grab / drag / release / shake`；拖移超过 2 个场景像素才视作拖拽 | 不是现实距离；未实测所有手势 |
| 掉叶和恢复 | 植物对象提供飞叶绘制和 `regrow`，Grow back 对当前显示植物执行恢复 | 不能由此证明 AI 复刻行为完全相同 |
| 自适应视图 | 单植物/全部植物布局、ResizeObserver、方向键切换、Enter/空格触发互动 | 代码含适配与键盘支持，不代表 390px 已验收 |
| 帧循环 | `requestAnimationFrame`，步进时间上限 1/30 秒，按观察到的帧间隔调整执行节奏 | 没有独立 FPS 或性能基准 |
| 原站声音 | `pP` 生成循环噪声，经低通/带通与 Gain 节点，随风力和叶量改变参数；声音由用户开关后 resume/suspend | 这是原站树林风声，不是作者风铃版的源码 |

原站存在 `/api/pixel-play/shakes` 统计入口及植物 JSON 请求。视频中 “Shaken … times” 不宜当成作者个人复刻次数、用户数量或性能数据。作者提示词里的“无网络请求”属于**其复刻目标**，不是原站当前的实际架构。 [S3]

### 4. 风铃扩展如何合理实现

以下是根据展示需求整理的**建议方案**，不是取得了 iam小韩 的风铃实现：

1. 用摆角、角速度、阻尼和共享风场描述铃管/纸签摆动。
2. 用接触或接近阈值加相对速度判定“敲击”，并加冷却时间，避免一帧反复触发。
3. 竹、铜管和玻璃各用不同的合成音色/包络，强风提高触发密度；不只是播放一个固定音频。
4. 使用 Web Audio 或 Tone.js 合成与混响，限制同时发声数；由用户手势启用音频。
5. 静音、暂停、减少动态效果和移动端触摸必须有明确行为。

Tone.js 的官方 README 确认浏览器用户手势后调用 `Tone.start()`，以及 Synth、PolySynth、NoiseSynth、信号控制与效果路由等能力。它证明这一方案的工具可行性，**不证明视频作者使用了 Tone.js**。 [S7]

### 5. 这条的真正方法论

把“照着这个好看的东西做”转换成五层合同：

| 层级 | 应写清的内容 |
| --- | --- |
| 视觉 | 布局、配色、像素尺度、轮廓、留白和控件层级 |
| 时间 | 摇摆节奏、回弹、掉叶、恢复顺序；不要只有一张静态参考图 |
| 状态 | Calm/Breezy/Storm、方向、强度、阵风、声音开关之间如何联动 |
| 输入 | 点击、拖拽、松手、键盘、手机触摸各自的预期结果 |
| 验收 | 对照画面和交互用例，记录差异；性能要给设备、视口、粒子数和测量方法 |

“一条提示词”是作者最终整理的输入形式，不代表整个制作过程没有截图反馈、迭代或调试。视频说明明确承认多轮调整，画面也展示了截图读取和操作。 [S1]

## 复现路径

### 本轮实际执行

- 取得并核对视频文件，读取完整说明与 11 张抽样画面。
- 用匿名浏览器读取 FeralUI 首页；拆读该次已取得的公开发布包。
- 从真实路由和 Download 链接追到 Pixel Play、itch.io 分发页，核对价格与公开许可回复。
- 固定三个参考仓库的 commit、README、package 和许可。
- **没有生成树林或风铃，没有取得/运行作者复刻代码，没有播放并验收合成声音，没有测量 1:1 或 50fps。**

### 建议的实现与验收顺序（未实际执行）

1. 先完成静态像素植物、布局与控件，冻结随机种子，避免每次截图换外观。
2. 加入点击、拖拽、回弹，再加风场、飞叶与恢复；每项单独比较。
3. 将天气预设变成状态配置，不让开关、滑杆和视觉行为彼此矛盾。
4. 验收手机布局、触摸、键盘、暂停和减少动态效果。
5. 再扩展风铃，验证碰撞到发声的关联、静音、用户启用音频和强风下声部上限。

不必为了几十秒演示直接引入完整游戏引擎。原生 Canvas/Web Audio 是一种方案；粒子、绘制或音频编排复杂后，再根据实际瓶颈选择 PixiJS、Tone.js。

### 可复用提示词骨架（本次整理，非作者原文）

> 做一个可离线运行的单文件 HTML 互动像素场景。绘制原创植物，不复制参考项目的 sprite、标志或品牌素材。先说明布局、像素网格和数据结构，再实现点击摇动、拖拽后回弹、掉叶和恢复。
>
> 让 Calm/Breezy/Storm、左右风向、强度与阵风共享同一份状态；控件值必须与视觉行为一致。固定随机种子，提供暂停、恢复、静音和减少动态效果选项，兼容触摸与键盘。
>
> 交付前检查控制台、网络请求、390px 视口和各项交互。性能按具体设备和粒子数量实测，不把设定的目标写成测试结果。对照参考列出仍有差异的地方，完成后再扩展风铃与用户手势启用的实时合成声音。

这是一份可执行规格的组织方式，不是对任意模型、一次生成、像素级一致或固定性能的保证；离线条件也与原站在线架构不同。

## 适用场景与限制

- 适合互动网页、小游戏、作品集或产品动效的学习与原型验证。
- 最有价值的是学习颜色、轮廓、运动节奏、状态联动和验收拆分；完整照搬原素材并不等于学会审美。
- 原作含手绘资产和关键帧，AI 从效果另做实现可能“观感接近但底层不同”；应区分视觉接近、交互等价与代码/资产复用。
- “没有开源仓库”不等于不能研究公开发布代码；“能下载素材”也不等于开源或可转售。
- 参考库的 MIT 许可不替代原素材授权。商业使用前核对具体下载包许可，不把评论中的许可扩大成整站许可。
